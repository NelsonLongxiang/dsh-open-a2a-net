# 多标签页布局并发 · 场景分析（调研卡交付 · 2026-08-29）

> 卡 5 交付：只调研，不改代码。现状：布局文档（`/__dsh_a2a/canvas-layout`）为单文档 last-write-wins，客户端 2D 规划画布每 800ms 防抖整文档 POST，5s 轮询 GET 采纳启发式（灯 idle/saved 且无在途手势且文档 JSON 有变化）。

## 冲突机制总览

两个标签页（T1、T2）各持完整模型与渲染，共享 host 端单文档。没有版本向量或资源锁，**唯一的真相时刻是 POST 返回的归一化回包**——而回包只被"自家保存"采纳。任何"对方在我两次保存之间保存了东西"的窗口都是静默丢失窗口。

## 场景时间线

### 场景 1 · 互相覆盖（最常见）

```
T1 拖节点 n1 → (100,100)     T2 拖节点 n2 → (900,200)
t0  POST save {n1@(100,100)} │
t1  ── 200 ok，T1 已存 ──    │ POST save {n2@(900,200)}（整文档，基于 T2 视野里的旧 n1）
t2                           │ ── 200 ok：文档里 n1 回退到旧位
T1 下一次轮询 GET：n2 回到旧位（T2 的写入被 T1 的旧文档覆盖）
```
**后果**：两边各自看来"保存成功"，但最终文档只剩最后写者的全部意图 + 前者的历史位。丢失是对称的、静默的。

### 场景 2 · 保存回包 vs 轮询采纳的采纳门竞态

```
T1 save 在途（灯 pending）
T1 轮询 GET 到达：返回的是 T2 刚写的文档
采纳门：灯=pending → 跳过采纳 ✓（设计如此）
T1 save 返回 ok:true → onAdopt(回包) → adoptExternalLayout ✓（自家回包永远采纳）
```
**结论**：该窗口被正确防御（save-loop 只采纳"发送时快照未变"的回包）；轮询 GET 的 lastLayoutJson 已盖戳不再重复采纳。**无丢失**。

### 场景 3 · A 删队、B 存帧

```
T1 散队「甲」（canvas POST remove → host 删除队与成员关系）
T2 不知情，继续布局，防抖保存 {frames:{"甲":…}, nodes:{…甲成员新位…}}
```
**后果**：布局文档里留下**孤儿帧「甲」与已离队成员的新坐标**。布局存储的注释自述"成员真相在 canvas.json，本store可随意重置"——帧只是矩形不产生路由语义，但视觉上会渲染一个指向不存在队的空框，直到有人拖动它触发一次不含甲的保存。**低危、自愈、但反直觉**。

### 场景 4 · 视口来回拉锯

T1 平移到世界 (0,0)，T2 平移到 (2000,1500)。两者每次滚轮/拖拽都标脏（800ms 防抖），视口 {x,y,scale} 随布局文档互相覆盖——**两边每 800ms+RTT 就把对方拽回自己的视野**。这是体感最差的一条：滚动浏览时画面"自己会跑"。

### 场景 5 · 同队双写（canvas.json 层，非布局层）

T1 拖 a 离队「甲」（remove-member），T2 同时把 a 拖入「甲」（add-member）。写面按到达序生效，**无丢失**（add/remove 都是完整语义），但成员序（路由优先级）由最后到达者决定——两端的 P 徽标显示在下一次轮询前是各自乐观的。

## 根因与候选方案（记录，不实施）

| 方案 | 内容 | 代价 |
|---|---|---|
| 1 · 布局文档加 `rev` 乐观锁 | save 携带所读 rev，host 不匹配 → `ok:false stale` → 客户端强制 GET+重放 | 契约 v2（锁定 v1 升版需评审）；客户端要处理 stale-retry 循环 |
| 2 · host 推送失效 | 任意写后 SSE/WebSocket 通知各端立即 GET | 需 host 新增推送面（超契约） |
| 3 · 客户端广播 | BroadcastChannel 同源互踢（保存时通知他端立即 GET） | 零 host 改动；只解决同源同浏览器，跨机器无效——而跨机器才是主要场景 |
| 4 · 维持 LWW + 文档明示 | 在 PR 描述/README 记录"多标签页布局互相覆盖"为已知边界 | 零成本；内网单用户多数场景一人一开 |

## 建议

内网单用户日常（一机一开）场景 1/4 几乎不可见；**真正的多标签并发需求出现时，从方案 1（rev 乐观锁）起步**，因为它同时给场景 3/5 提供检测点。当前先在 README 已知边界处留一行说明即可。
