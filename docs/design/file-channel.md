# 设计：A2A 文件通道（#91）——发引用、按需拉取

- **状态**：提议稿（路线图 #65 P3）。实现按 §7 分片推进。
- **归属**：dsh-open-a2a-net。文件通道是跨项目接口：各项目的坐席都靠它传文件，所以按协作规范 v1.18 属**高档**。实现 PR 需要一个非自我节点的评审 PASS，评审方最好来自用这个通道的项目。
- **关联**：#90（事故）、#91（裁决：文件不走会话消息）、`src/flood-guard.ts`（过渡期防洪，已合入）、#112/#113（CLI 侧幂等与信箱丢件）、N4 会话污染（docs/design/node-identity.md §6）。

## 0. 一句话

文件不进会话消息。发送方宿主把文件按内容寻址暂存起来，会话里只发一条带引用的消息（sha256、大小、名字、来源主机）。接收方需要时一次拉取，校验 sha256 后落到自己的工作区，再照常回一条回执。一个文件对应一条消息和一次拉取。

## 1. 现状

- **JPFILE-PART v1**：把文件切成分件，每一件是一条独立的 `/a2a/direct` 会话消息。2026-10-29 的事件里，一次传输就把接收会话冲到了上下文超限（#90）。
- **过渡防洪**（`src/flood-guard.ts`，docs/protocol/direct-flood-guard.md）：
  - 每个发送方每分钟最多 16 次新投递；
  - 每个 JPFILE 传输累计最多 16 件；
  - 超限时可见拒收，返回 `-32008`。

  它只是踩刹车，没有给文件一条自己的路：16 件以内的文件照样进模型上下文，大文件则传不了。
- **现有上限**：一次 `/a2a/direct` 请求体最多 512 KiB（`MAX_ROUTE_BODY_BYTES`，超出返回 `-32001`）；CLI 信箱每条消息最多 4000 字符，最多保留 64 条（#113）。这两条路本来就不是为传文件设计的。

## 2. 三种做法

| | A. 发送方暂存、接收方拉取（推荐） | B. 推送到接收方宿主 | C. 第三方对象存储 |
|---|---|---|---|
| 字节怎么走 | 接收方宿主向发送方宿主 GET 一次 | 发送方宿主向接收方宿主 POST 一次 | 双方各连一次外部存储 |
| 谁占存储 | 发送方，自己的文件自己管 | 接收方，要防别人往里灌 | 外部存储 |
| 准入 | 沿用 OriginClaim：拉取方要证明自己是授权的那个队 | 接收方还要再加一道上传配额和准入 | 外部存储的凭证另管 |
| 主机互不可达 | 接收方连不上发送方时失败 | 发送方连不上接收方时失败 | 双方都能出网就行 |
| 新依赖 | 无 | 无 | 有：凭证、账单、外发 |

**选 A**：存储和配额落在发起方，接收方不会被灌；准入完全复用现有的 OriginClaim；不引入任何外部依赖。主机之间不可达的情况，第一版只给出可见的失败（§3.6），推送作为第二版的备选。

## 3. 协议（方案 A）

### 3.1 暂存与授权

发送方会话调用新工具 `a2a_file_send { path, team, note? }`。宿主依次做下面几件事：

1. 读取会话工作区里的 `path`。同机信任模型下（node-identity.md §7），它能读的范围和通用文件工具相同。单个文件最多 **64 MiB**，超出就拒绝，不截断。
2. 计算 sha256，存成 `<home>/a2a/blobs/<sha256>`。内容相同的文件只存一份。
3. 记一条**授权**：`{ sha256, size, name, to: <目标队或句柄>, by: <发起会话>, expiresAt: 现在 + 24h }`，写进 `a2a/blob-grants.json`。
4. 用现有的 `a2a_route`（异步）给目标发**一条**消息：

   ```
   [A2A file] v1 sha256=<64hex> size=<bytes> name=<名字> from=<本机卡片 URL>
   <note>
   ```

5. 工具返回 `{ ok, task_id, sha256, size, expiresAt }`。

同一个 sha256 发给同一个目标，只续期授权，不再存一份。发给不同的目标时，每个目标各有一条授权，`blob-grants.json` 里按 (sha256, to) 并存，各自过期，文件只存一份（设计评审 PASS 附注 b）。只要还有一条授权有效，这个 blob 就不会被清掉。

**容量**：全宿主最多 1 GiB 或 256 个 blob。满了先清已过期的；还不够就拒绝新的暂存，返回可见错误，不挤掉还没过期的授权。

### 3.2 拉取

接收方会话读到 `[A2A file]` 消息后，按需调用 `a2a_file_fetch { ref }`，`ref` 就是整行引用。宿主依次：

1. 解析引用，得到 `from` 的根 URL。走 `peerFetch`（#195），`isolated` 打开时直接拒绝。
2. 发 `GET <from>/a2a/blob/<sha256>`，请求带 `caller_session` 和 OriginClaim 头（绑定受众的 v2）。
3. 边收边算 sha256，同时计数；超过声明的 `size` 立即中止。收完后 sha256 和大小必须都对得上，否则丢弃临时文件，返回校验失败。
4. 落到会话工作区的 `a2a-inbox/<sha256 前 12 位>-<名字>`。名字里的路径分隔符和 `..` 一律替换掉，只能落在 `a2a-inbox/` 下面。
5. 工具返回 `{ ok, path, size, sha256 }`。

**发送方宿主的 `GET /a2a/blob/<sha256>`**：
- 准入要求 OriginClaim 验证通过，并且是绑定 v2 加根 callerUrl，与工作台「已验证来源」的条件相同；匿名请求和未验证的请求一律拒绝。
- 调用方的队必须是授权里的 `to`；`to` 是 canvas 队时，调用方须是它的成员；授权已过期也拒绝。实现（F1b、F2）细化如下：
  - **主机签名方**：`to` 等于调用方本人；或者是签名主机本身，即授权给整个 zone；或者是签名主机自己的 canvas 队，由那台主机自己管成员；或者是本机的 canvas 队，而且调用方**本人**就是成员。授权给同一主机上另一个会话的文件，不归这个会话（F2 收紧：诚实主机的工具写的是正在拉取的那个会话，失误不会跨会话）。
  - **CLI 句柄**：只认同名授权，不当 zone 用（#208 评审 R1）。
  - **限速**：按已证明的签名方计，主机按 zone，CLI 按完整句柄。
- 每个调用方每分钟最多拉 16 次，复用 FloodGuard 的窗口。
- 没有列目录的接口。sha256 猜不到，但它不是秘密，真正起作用的是授权。

### 3.3 回执

接收方照常回 `[A2A receipt] task <task_id> <结果>`，发送方台账上那一行照常结清，台账和守恒计数（#154）都不用改。拉取本身不算回执：拿到文件不等于事情办完。

### 3.4 CLI 身份

- **发送**：`a2a-net file send <path> <team>`。CLI 通过控制面 `POST /__dsh_a2a/blob`（受 apiKey 门禁，请求体是原始字节）把文件暂存到自己的 home 主机，再发引用消息；引用里的 `from` 是 home 主机的卡片 URL。
- **拉取**：`a2a-net file fetch <ref> [--out DIR]`。CLI 自己签 OriginClaim 去拉，校验规则和宿主一样。

### 3.5 和 N4 会话污染的关系

`a2a_file_fetch` 拿回来的是本机以外的内容，它的结果一律算远端内容：加进 `A2A_READ_TOOLS`，`peerContentOf` 恒为 true。这样拉过文件的会话，此后的自我更新会转人工审核。

之后模型用通用文件工具读这个文件，属于 §6 已声明的边界：不会再打一次标，但拉取那一步已经打过了。

`a2a_file_send` 读的是本机文件，文件本身不打标。但它经路由主干发出引用消息，路由结果里可能夹带对端的文字，所以和 `a2a_route` 一样，读宿主最后写入的 `peer_content`：走过对端就打标，本机路由不打标（F2）。

### 3.6 失败形态

失败都是可见的，不静默。新增的 wire 错误码接在现有序列后面，登记在 docs/protocol/delivery-origin-auth.md。

| 情况 | 结果 |
|---|---|
| 文件超过 64 MiB，或存储已满 | `a2a_file_send` 返回 `ok:false` 和原因，不发消息 |
| 接收方连不上 `from` | `-32009 file-origin-unreachable`，附提示：对方主机不可达，请对方改用可达的 home 主机发送 |
| 授权不存在、已过期，或调用方不是 `to` | 发送方返回 403 加原因码；接收方工具把原因码原样给出 |
| sha256 或大小对不上 | `ok:false`，原因 `digest-mismatch` 或 `size-mismatch`，不落盘 |
| `isolated: true` | 拉取直接拒绝，原因 `isolated`；本机暂存和发送照常 |

## 4. 与 JPFILE-PART 的过渡

1. 文件通道合入并部署后，FloodGuard 遇到 JPFILE-PART 消息时，响应增加 `advice.reason: use-file-channel`，并附上 `a2a_file_send { paths, team }` 与 `a2a-net file send <path…> <team>` 的用法；16 件以内仍按原规则放行，只附提示。超限仍以 `-32008` / `file-parts-exceeded` 拒收，错误文本也带迁移提示。
2. 机群全部升级后的下一个版本，JPFILE-PART 一律拒收。这一步按 v1.18 属高档，要有非自我评审。

过渡期内 16 件的上限保持不变。

## 5. 安全与边界

- 授权只认 OriginClaim 证明过的身份。调用方自述的 `caller_session` 只用来定位授权，不能代替证明，和 #172 / #179 的口径一致。
- blob 只按 sha256 寻址，按授权放行。发送方宿主不接受任何外来写入：暂存只能走本机会话工具，或带 apiKey 的控制面。
- 落盘路径受限在 `a2a-inbox/` 下面，名字一律清洗，不跟随符号链接。
- 存储和授权都在本机持久化。文件读不出时，授权按空处理：已发出去的引用拉不到，但不会误放行。

## 6. 不做的事

- 不做分块续传和 Range 请求。64 MiB 以内一次拉完，失败就整份重拉。
- 第一版不做推送（方案 B），也不做中继转发。主机互不可达时的方案另开 issue。
- 不做加密存储。blob 和工作区文件一样，在本机明文保存，同机信任模型下与通用文件工具一致。
- 不改台账和回执协议。

## 7. 实现切片

| 切片 | 内容 | 档 | 判据（反例） |
|---|---|---|---|
| F1 | blob 存储加授权（`src/blob-store.ts`）、`GET /a2a/blob/<sha256>` 准入、容量 | 高 | 未授权、过期、非 `to` 的调用方都拿不到；存储满时可见拒绝；没有 OriginClaim 证明的请求被拒 |

## 8. 默认值（按 v1.18 由实现方决定，这里写明）

- 单个文件 64 MiB；全宿主 1 GiB 或 256 个 blob。
- 授权有效期 24h。
- 拉取限速：每个调用方每分钟 16 次。
- 落盘目录：`a2a-inbox/`。

这些值都写成常量，改动时连同反例测试一起改。
