# superagent: ygl-trees as the team's memory

Status: agreed with the owner on 2026-11-10.

## Context

A2A carries a team's work and its receipts. What the team learns, the evidence behind it and the decisions it made should outlive one session, so the owner asked the team presets to make ygl-trees part of the work. A live ticket on the test host showed that a persona line alone is not enough: the router looked up earlier work before deciding, but the member did the research without reading or writing ygl-trees at all.

## Decisions

- **Y1 Reach: the MCP server, narrowed per role.** The three presets mount `dsh-mcp-client` with `ygl-trees mcp` as server `ygl` (#556). The server runs outside the session's sandbox, so every team session reaches one shared workspace: the team's own (`YGL_HOME`, from `SUPERAGENT_YGL_HOME` or `~/.ygl-trees-superagent`), apart from the owner's personal one and created once with `ygl-trees db init`; the CLI in a session's shell reaches only its own directory. The router gets `mcp__ygl__read` only; members and observers also get `mcp__ygl__write`, `mcp__ygl__verify` and `mcp__ygl__doctor`. Without `ygl-trees` on the host's PATH the tools do not appear, and the plugin installs nothing.
- **Y1f The single tool (2026-11-25).** ygl-trees PR #311 adds `mcp__ygl__trees` (`{domain, action, params}`, `help` to discover, contract `ygl-trees/1`, unknown routes refused) and keeps the old four tools for one release. Every role also has `trees`. Owner's option A: the host narrows the router's `trees` calls to `help` and exactly the routes the old `mcp__ygl__read` offered (`YGL_TREES_READ_ROUTES` in `role-tools.ts`, taken from ygl-trees `546976ac`); members and observers keep every route, as with the old tools. Assignment cards name `trees` only when the member's session has it, so a host still on an older ygl-trees keeps today's wording. Removing the old names waits for the next release.
- **Y1a One ygl-trees session per team session (2026-11-10).** DSH starts an MCP server with `DSH_*` removed from its environment, and a preset's config is the same for every session, so without more every team session shared ygl-trees' default session and its project selection (found on the owner's host). The mount starts the server through a shell that sets `YGL_SESSION` to `superagent-<pid>` (on Windows, `cmd` with a random number), so each process has its own; the personas pass `project` on every read and write rather than rely on a selection. The id is per process, not the DSH session id: binding it to the session needs DSH to hand the session to an MCP server, which it does not.
- **Y1b The host creates the workspace (2026-11-10).** `db init` is an administration command the MCP server does not offer, the router has no shell and a member's shell reaches only its own directory, so on a host where nobody ran it every ygl tool answered `no database` (owner's Windows host). At start the host runs `ygl-trees db init` with `YGL_HOME` set to the team's workspace when it has no `ygl-trees.db`; without the command it does nothing. The personas say that `ygl` is only the MCP server's name, the command is `ygl-trees`, and a missing database is the host's to fix, not a session's.
- **Y1c One project per team (2026-11-11).** A new team's workspace had no project, so a member's first evidence or claim failed (`no project selected`) and nothing said which project to use; with several teams on a host they would share or collide. Each team has the project `team-<canvas>`. The host makes it (idempotent `project new`, under its own `YGL_SESSION`) when the team starts and before its cards go out. The assignment card names it: the member selects it for its own session (ygl-trees' MCP `agent brief` ignores an explicit project, ygl-trees#260) and passes it on every other call, and makes no other project. The router's candidate card names it for the router's `kb search`.
- **Y1d The cards follow the installed version (2026-11-18).** At start the host reads `ygl-trees --version` and shows it on the team state (`ygl`); the team engines start once that bounded read has settled, and until then no candidate or assignment goes out on any entry: a request is taken and waits (#739 review R1). From 0.123.0 the MCP `read agent brief` honours an explicit project (ygl-trees#260), so the card drops the `project use` step and passes the project. Below that, or when the version cannot be read, the card keeps the step. The host also stops re-running `project new` on every start: it lists the projects first and makes the team's only when it is missing (161 runs had made 10 projects on the owner's host). The member and observer personas no longer tell a session to make a project when none fits; they follow the card, and without a card they ask for the team's project.
- **Y1e Each team's kb notes have their own scope (2026-11-18).** kb notes belong to no project, so every team's search found every other team's notes. From ygl-trees 0.126.0 a note carries a scope: a team's is `bench:team-<canvas>`; a canvas name outside ygl-trees' id characters becomes `bench:teamh-<hash>`, a form no literal name can produce. The host starts the team engines only after its version read has settled, so no card goes out with the oldest steps on a host that has 0.126.0. The member's card says to `kb add` with that scope and to search it first, then the unscoped notes from before scopes; the router's candidate card says the same. Notes written before stay unscoped and are not moved: which team wrote each cannot be told reliably. Below 0.126.0 the cards say nothing of scopes.
- **Y2 The steps are on the assignment card.** A member that has `mcp__ygl__write` finds the steps in the card it acts on: read `agent brief` and `kb search` first, record evidence and claims as it goes, `kb add` before ready, and pass the ids it wrote in `ygl` on `a2a_ticket_report`. The ids are added to the report's summary, so the router and the owner see them.
  - **Skills and the ticket's task (2026-11-21, owner agreed).** A read of a team library found sources, evidence, claims and kb notes in use, but queries, relations, tree nodes and tasks at 0 and every skill with 0 hits: the card asked for none of them. The card now also asks, first, for `agent match` with the ticket's subject (a named skill is read with `skill show` before work), and, when the member takes the ticket, for a task in the team's project titled after the ticket, advanced to `doing`; before ready it is advanced to `done` and its id goes on the report with the others. The ygl MCP passes no project on `task advance`, so in a library with several projects advance answers "ambiguous project"; the task step therefore selects the team project for the session (`project use`) before add and advance. This is the only place a 0.123+ card still uses `project use` — Y1d's reason (brief takes the project) holds for the first step — and it can go once the MCP passes the project on advance.
  - **No `rel attach` on the card yet.** The MCP `rel attach` always attaches from a tree node (`node:<key>`), and the node must exist in a tree of the project; a team project has no tree, so every such call would fail. Relations wait for the owner's separate decision on each team's milestone tree; claims keep linking to evidence with `claim-link` as before.
- **Y3 One reminder at ready.** A ready report from such a member with no `ygl` ids is sent back once (`code: ygl-record`). The next ready goes through with or without ids, so a ticket with nothing worth keeping is never held, and the reminder is not a gate the member can get stuck on.

## Consequences

The host cannot tell whether what a member wrote is worth keeping; it only makes the step hard to forget. The reminder is kept in memory, so after a host restart a member may be reminded once more. A member serving another host's team is not reminded: its report goes to that host.
