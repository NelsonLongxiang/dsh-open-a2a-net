# superagent: preparing a ticket's directory, a cap on running tickets, and a health check

Status: agreed with the owner on 2026-11-10 (category one of the upstream comparison).

## Context

Upstream superagent prepares each ticket's directory with a command, caps how many tickets run at once, and checks the service every hour. Here a member is told to make its own worktree, nothing caps the team, and problems show only on the team page.

## Decisions

### Preparing a ticket's directory

- **R1 One command per team.** The team may set a prepare command. Before a local member gets a ticket's assignment card, the host runs it once with `sh` in that member's workspace, with a ten-minute limit by default. A ticket is prepared once: a later assignment of the same ticket does not run it again.
- **R2 What it is told.** The command gets `SUPERAGENT_TICKET_ID`, `SUPERAGENT_TICKET_NAME` (the name the ticket's directory or worktree takes), `SUPERAGENT_REPO` and `SUPERAGENT_MEMBER` in its environment. A typical command makes a `git worktree` under `.worktrees/$SUPERAGENT_TICKET_NAME`.
- **R3 A failure is visible and retried by the owner.** A failed or timed-out command records its exit and the end of its output on the ticket as a delivery failure, frees the member, and leaves the ticket waiting for a person. A retry runs it again.
- **R4 Only the owner sets it.** The command runs as this host's user, outside any sandbox, so writing it needs the GUI login as rule edits do. A member on another host does not run it: its host is not this one.

### A cap on running tickets

- **R5 New tickets wait at the cap.** The team may cap how many tickets run at once; 0 means no cap beyond one ticket per member. At the cap a new ticket waits as queued. A ticket coming back to its member because a person answered it is not held back by the cap, so a person's message is never stuck behind new work.

### The health check

- **R6 Problems are computed on the host.** The host lists the team's problems, among them a router or member session that is not loaded and a ticket with no activity for an hour. The team page and both right-bar views show them, so a problem is seen from the conversation too.
  - **The router's failed turn (2026-11-12).** When the router's turn fails (its model refused: a used-up quota, an outage), requests wait unjudged and nothing else shows why. The host keeps the latest failure in memory and lists `router-turn-failed` with the error and how long ago. The router's next routing call clears it, and so does a restart. *Found live:* two child teams' routers hit their model quota (429), and the root team saw nothing.
- **R6a Queued tickets say what they wait for (field report 2026-11-19).** A queued ticket has no binding, so the hour-quiet check never saw it: on one host eleven tickets sat queued for days beside four idle members, with health empty. The host now names tickets queued longer than the quiet time, one problem per thing they wait for: the member a ticket is kept for (busy, or no longer on the team), a repository none of whose members is free or present, every member busy, or the team's concurrency cap. A free member whose delivery was refused is named with that member (`delivery-refused`, the last refusal kept in memory); a ticket with a free member that has still not gone out after the quiet time is `launch-stalled`, cause unknown, so a refusal the host did not see cannot hide it either (#744 review R1). A paused team reports its queue as `paused` and raises nothing for it: the page already shows the pause. The problem carries how many tickets and the oldest one, so a busy member behind eleven tickets raises one reminder card. A member that left or a repository nobody works in is shown as danger, since waiting does not clear it. The state lists each queued ticket with its reason, member or repository and since when; `superagent_read` (router) and `a2a_ticket_read` (observers) show the same under `queue`. `superagent_assign` says what the host already did: a ticket that has not started can go to any member at any time.
- **R7 A problem that stays tells the owner (2026-11-10, 对照上游「每小时检查，出问题才告诉你」).** Every 15 minutes the host looks at its health and raises one decision card (P2, 去处理 or 先忽略 24 小时) for a problem that is new; the same problem while it lasts raises nothing more, and a problem that goes away takes its undecided card back. A decision holds its reminder off — a day for 忽略, an hour otherwise. The boot grace period raises nothing (R6 keeps health quiet then, so nothing reaches the cards either). Each team's host keeps its own reminders; no session is started and no A2A route is sent. A health card's decision opens no ticket: both options only dismiss it. The 忽略 hold-off lives in memory only: after a restart a still-present problem raises its card again before the 24 hours are up, which reads as an early reminder rather than a lost one. The card's question uses the banner's own words, not the internal codes.
- **R7a The observer sees it first (workbench-market 18 §八; the owner authorized the market session to settle it, 2026-11-20).** This changes R7's recipient: fewer health cards reach the owner. When the team has an observer (D19) whose session is loaded and the problem is not about that observer, a new problem goes to it as a `[superagent health]` notice carrying the token `[健康 <problem key>]`, and no card is raised. The observer handles it by filing a request (`a2a_ticket_request`) or raising a card (`a2a_decision_propose`) whose text carries the token; reading it, or only saying something in its session, does not count. A handled problem is held off for an hour, as a decided card is, and the observer is told again if it lasts. The owner gets R7's card, saying why, in three cases: the team has no observer; the observer's session is not loaded (when told, or at a later look); or an hour (the health check's quiet period) passes without the observer handling it. Because the host looks every 15 minutes, that card comes 60 to 75 minutes after the notice. A notice that cannot be delivered goes to the owner at once. An exception while selecting the observer or delivering its notice is contained for that problem: the owner card records that observation or delivery was unconfirmed, no false observer hold is retained, and the other problems in the same check are still considered. This fallback does not retry the underlying business work. Who was told, and when, is kept in the team's `observer-health.json` (#754 review): a restart neither tells the observer again nor restarts its hour, so a host that restarts more often than once an hour still puts an unhandled problem to the owner. The hold-off after the observer acts stays in memory, as R7's does. Credential-access audit cards (local market trial, 2026-11-11) are not health-check problems and still go straight to the owner. Chapter 18 also counts deciding the card as an approver (`a2a_decision_decide`) as handling it; while the observer holds a problem there is no card, so only a request or a card counts. The observer reads the health list with `a2a_ticket_read` kind `health`.
- **R7b A member's question goes to the observer first (workbench-market 18, #880; owner via the coordinator, 2026-11-20).** When a member reports a question for a person (`a2a_ticket_report` with `question`) and the team has a loaded observer other than that member, the observer is told first with a `[superagent question]` notice carrying the token `[提问 <ticket>]`. The person path waits meanwhile: the router's report says the observer has it and not to forward it yet, and the ticket's decision card is not listed. The observer settles it with a note on that ticket (`a2a_ticket_note`, a fact for the holder that grants nothing and cannot change, stop or reassign the ticket), a request (`a2a_ticket_request`) or a card (`a2a_decision_propose`) whose text carries the token. The question goes on to the person by the existing route, unchanged, when the team has no observer, the observer is not loaded (when told, or at a later look), the observer does not settle it within an hour, or the ticket still waits on its question an hour after the observer settled it (backstop). The person's clock (workbench-market 15: a day unanswered also reaches the domain lead) starts when the question reaches the person: the ticket card's `at` is that moment, and the observer's hour is not counted. A member asking again while the observer still holds the question does not restart its hour (the observer hears the new words); once the observer has settled a ticket's question by any of the three ways, a new question on it within the hour goes straight to the person, so the two cannot loop (#761 review). The host looks every 15 minutes with the health check, so a pass-on lands 60 to 75 minutes after the notice. The gate's state is kept in the team's `observer-questions.json`; a restart neither tells the observer again nor restarts an hour.
- **R7c The observer casts a card (observer phase 2, T5-A; off by default).** While the owner has turned the team setting `observerCast` on, the observer may cast one card from the host's prompt-template library into another session of its own team with `a2a_card_cast` (session, card, a one-line reason). The a2a host checks who may: the calling session must be the team's observer, the target must be the router or a member of this team other than the observer itself; the prompt-template plugin (0.17+, `ctx.promptTemplates.cast`) recognizes the caller as the a2a plugin from its loader entry and checks the rest (switch `cast.enabled`, card scope, one-line reason, one copy per card per session). The card goes into the target at its next step as a visible message naming the caster and reason, and the host wakes the target with a `[superagent card]` notice that carries no instruction. Without the plugin's service the tool answers `available: false`. Every cast is logged by the plugin as `source: plugin`. Turning `observerCast` on is a rule change that needs the owner's browser proof; a control-route shell cannot (#764 review). Per target session the host allows at most 3 casts an hour (a 4th answers `rate-limited` before the plugin is asked) and one wake per 15 minutes (later casts in the window wait for the session's next step); the counts are kept in the team's `observer-casts.json` across restarts.
- **R7d Cast basis and the queue (#902 S1).**
  - **Basis.** Every `a2a_card_cast` names its basis, and the host checks it before the plugin is asked; a bad basis answers `basis`. The basis is one line of at most 200 characters, in one of three forms:
    - `ticket:<id>`: a ticket of this team, named by its id or an unambiguous prefix of 8+ characters;
    - `event:<id>`;
    - `none: <a sentence>`.
  - **The plugin's side (dsh-prompt-templates, after #86).** It shows the basis in the card's header and records it in the intervention log. It keeps the queue in its database, so a queued card survives a host restart; each row ends as `delivered`, `withdrawn` or `expired`. Each library card carries `kind` (`workshop` for agent-atelier cards, `template` otherwise).
  - **`a2a_card_queue`.** The observer lists its own team's queued casts (no text) or withdraws one that still waits. Rows of other teams' sessions are never shown or touched. A host whose plugin lacks the durable queue answers `available: false`.
- **R7e The observer's own cards (#902 S2; off by default).**
  - **Switch and limit.** The team setting `observerCardDraft` turns this on; it is a rule field, so only the owner's browser proof sets it. A team keeps at most 50 of the observer's own cards.
  - **`a2a_card_draft`.** While the switch is on, the observer writes its own cards with it: list (default), create, update (by id) or delete (by id).
    - A card is an ordinary template of the observer's own session, written through the prompt-template plugin's `draftCard` (dsh-prompt-templates #87).
    - Each card names the members it is for (`for`: sessions of this team other than the observer, or `["team"]`), a one-line scene, and optionally the library card it adapts (`from`).
    - The team keeps `for`, scene and `from` in `observer-cards.json`; they are also written into the template's description.
  - **Casting one.** `a2a_card_cast` with such a card answers `not-for` for a member outside its `for` list. Otherwise it passes the observer as `authorSession`, and the plugin then lets the observer's own card go into that member, marked 「定制·」. A library card is cast as before.
  - **Older plugin.** A host whose plugin lacks author-session cards answers `available: false`.
- **R7f How a cast goes in: trigger and release (#902 S3).** `a2a_card_cast` takes `mode`.
  - **`insert` (default).** As before: the card goes in at the target's next step, and the target is woken at most once per 15 minutes.
  - **`queue`.** The card waits for the first step of the target's next turn and never cuts into a turn under way; the target is not woken. The plugin side is dsh-prompt-templates #88 (`mode` on `cast`, a `mode` column on `cast_queue`).
  - **`trigger`.** Only into an idle member, never the router. The card is queued and the target is woken now, at most once per 30 minutes per target. A busy target is refused with `busy`; a host that cannot tell idle answers `available: false`.
  - **`release`.** The cast is armed on the a2a side and goes in once, later, when its condition holds:
    - `when`: `ticket:<id> <stage>` (person, person:<action>, working, idle or ended), `idle:<minutes>` (10..1440, the target stays idle that long), or `at:<ISO time>` (5 minutes to 7 days ahead).
    - `then`: insert, queue or trigger. A trigger that finds the target busy is queued instead.
    - Every check and limit of a cast (the switch, the team, the card, the hourly limit) runs again at release time. A refused release ends `failed` with the refusal kept, and is not tried again.
    - It expires after `expires_hours` (default 24, at most 168). A session holds at most 5 armed releases. They are kept in the team's `observer-releases.json` and looked at once a minute, so they survive a restart.
  - **`a2a_card_queue`.** It also lists the team's releases (armed, released, expired, withdrawn or failed, with the result) and withdraws an armed one by its id (`r-…`).
- **R7g The owner's 待投卡 (#902 S4).**
  - **Settings (rule fields: the owner sets them — the browser owner, or the owner's delegate with each use audited, as for every rule field; a session never does).** `castOff` lists the team's sessions the observer may not cast into; a cast into one is refused with `member-off` in every mode, and an armed release for it fails when it comes due. `observerTriggerRouter` lets the observer trigger the router; without it the router takes only insert and queue.
  - **The team state's `casts`.** The switches (`on`, `draft`, `triggerRouter`), `off`, the casts still waiting in the plugin's queue for this team's sessions, and the armed releases, without card text or the observer's id. A host whose plugin lacks the durable queue reports `available: false`.
  - **The team page.** The 团队 view shows 待投卡: the three switches, each target's casting on or off (the observer itself is not a target), and each waiting card and armed release with its target, mode or condition, reason and basis, and a 撤回 button.
  - **`cast-withdraw`.** The control route's POST action withdraws one waiting cast (`session_id`, `id`) or armed release (`r-…`) of this team; it needs the owner's browser proof. Another team's rows are never touched.
- **R7h Pre-release review fixes (#902 review of #907, #908, #910; plugin side dsh-prompt-templates #89).**
  - **Capabilities (#910 B1).** The plugin declares `castCapabilities()`. Without a declared `queue` mode, queue, trigger and release answer `available: false`; only insert goes to an older plugin.
  - **Event basis (#907 B1).** `event:<id>` must name a trigger this team recorded; anything else is refused, and the observer writes `none: <what it saw>`.
  - **Attribution (#907 B2).** Every cast carries an origin `a2a|team:<canvas>|observer:<session>|mode:<requested>[|release:<id>]`, kept by the plugin in its queue and intervention log.
    - Lists show only this team's rows (a row of another team on a shared session is never shown or touched). A row without an origin carries no evidence of its team, so no team view lists or withdraws it (#913 review); such rows end within the plugin's one-hour wait.
    - The observer withdraws only what it cast (`mine`); the owner, anything of this team. No row shows the observer's session id.
  - **Delivery (plugin #86 B1, #88 B1; #89 review).** A row becomes `delivered` only once the session's log shows the cast message naming it, with its intervention record (delivery mode and origin) in the same transaction. A sent row the log does not show, or whose log cannot be read, stays sent: absence is not proof, so it is never sent again on that ground.
  - **What is reported (#910 B2).**
    - The wake is reported as `sent`, `not-live` or `failed`; `woken` is true only when sent. A cast whose limits could not be saved says `limitsRecorded: false`.
    - Arming or withdrawing a release that cannot be saved is refused and changes nothing.
    - A release is written `releasing` before its cast; after a restart it is settled by asking the plugin for the exact origins it could have cast with (found: released, `reconciled`; none: looked at again, the plugin's own filter being the proof). A plugin that keeps no origin, or a failed read, ends it failed as `uncertain` rather than casting twice.
  - **Event conditions.** `when: event…` is refused as not available yet; S3 ships ticket, idle and at conditions only.
  - **Custom cards (#908 B1).**
    - Each record keeps its author. After an observer handover the new observer cannot edit, delete or cast the old one's cards (`not-yours`); lists show `mine`, not the author.
    - Delete removes the record only when the template is gone: deleted now, or already absent (`reconciled`).
    - An edit is marked `pending` on disk before the plugin's text changes; a card left pending is not cast until a save completes it. A new card whose record cannot be written is taken back from the plugin; if that fails too, the answer names the orphan.
- **#911 review fixes (S4).**
  - **Who sets and withdraws.** `castOff`, `observerTriggerRouter` and `cast-withdraw` take the owner's proof like every rule field: the browser owner, or a live owner delegate whose use is audited; an unknown or revoked delegate is refused with no browser fallback. The HTTP face tests cover both, and that a refusal changes nothing.
  - **Turning a member off.** It also withdraws this team's casts still waiting for that member and its armed releases (`member-off`); the settings answer says how many were withdrawn and which were not (a card already handed to a step, or one the plugin refused). Other teams' rows are left alone.
  - **Moved members.** A cast is this team's by its origin, so a cast for a member that has since left is still listed and the owner can withdraw it; the observer cannot. Releases live in the team's own state, wherever their target sits now.
  - **What leaves the host.** Only whitelisted fields of a plugin row reach the team state and the tools (id, session, template, name, version, caller, reason, basis, times, state, mode), plus `requested`, `release`, `legacy` and `mine`. Card text, the origin string and the observer's session id never do.
- **#903 S1 review fixes (#906).**
  - **`user builder … --all`.** Reads every saved node. A 401, a missing delegate, a dead node or a bad reply on one node is reported for that node, and the rest are still read. `--json` prints `{ ok, nodes, failed, results }`; the exit code is 0 only when every node answered.
  - **`view=builders`.** It also lists builders that are not loaded now, from the host's own notes of sessions it saw running the builder preset (`<a2a home>/builder-sessions.json`). A noted session seen under another preset, or taken onto a team, is forgotten.
- **R7d The session idle sweep (observer phase 2, T5-B; off by default).** While the owner has turned the team setting `idleSweep` on (a rule change: it needs the owner's proof), the health check reads each ticket-holding member's wrap-up self-check log from the same host's dsh-prompt-templates (`ctx.promptTemplates.selfChecks`, and only while its `selfCheckEnabled()`) and adds up to three problems, which reach the observer first (R7a): `session-wait-overdue` — the latest word is a registered wait whose deadline (an ISO time) has passed; `session-orphan-stop` — the latest word is an orphan stop; `session-no-selfcheck` — the member has held its ticket for the quiet hour with no self-check record at all (the check never ran: an error, an interruption, a session not loaded). Only rows written since the member's current Assignment began count, so an earlier ticket's ending never speaks for this one; the latest word is the latest `orphan` or `concluded` row, and the rows the check writes along the way (`written`, `hint`, `no-template`, `injected`) never hide it. A deadline that is not a time says nothing, and so does a host without the plugin's log; a member whose log read throws is skipped and the rest are still swept. For the self-check's own precondition this plugin provides `a2aTickets.hasOpenTicket(sessionId)`: whether any team's executor holds a ticket for that session (undefined when the host runs no superagent team). It is visible to every plugin on the same host and answers about any session across this host's teams — a yes or no only, never the ticket; same-host plugins are already trusted, and it never crosses hosts.

## Consequences

The prepare command is as powerful as a shell on this host. Nothing checks what it does beyond its exit status.

A host that has just started wakes its joined sessions one by one; until that is done, or for its first two minutes, a session not loaded yet is not reported.
