# 0.8.1 升级 / 回退 / 可复现候选检查

## 授权边界

目标 0.8.1-preview.30（0.8.1 的预览版，npm 上用 `preview` 标签，`latest` 不动），取代已打标签、未发布的 0.8.0；npmjs 上相对 v0.7.0。本文是升级核对材料，不是部署声明（preview.30 为候选、尚未发布；preview.29 已于 2026-11-23 发布到 npm 的 `preview` 标签，发布包与钉定候选字节不同、内容逐文件相同，见 [release.md](../release.md)）：不打 tag、不 publish、不改生产配置、不碰凭证。发版 PR 经非作者精确头评审 PASS 后合入；tag、registry 发布与各节点部署由属主另行安排。

公开命令里的目录、服务入口和节点都用占位符，执行者替换成自己的已核准值，不在公开报告里回填网络或环境细节。

本版沿用 [0.8.0 升级检查](0.8.0-upgrade-check.md) 的全部内容；下面只写差别。

## 0.8.1 补充

- **Windows（#901）**：宿主能解析到 ygl-trees 入口脚本时直跑 node；解析不到照旧，可用 `SUPERAGENT_YGL_BIN` 手动指定（见 docs/ops/superagent-mcp.md）。
- **升级后核对**：a2a 插件正常加载；团队会话的 ygl 工具可用（新版 ygl-trees 下有 `trees`）；Windows 节点开团队会话不再弹 cmd 窗口。

## preview.30 补充

相对 preview.29 新增三个配置键（`receiptBypassProgressMax` 默认 20、`receiptBypassProgressIntervalMs` 默认 60000、`receiptBypassAttentionMax` 默认 20），没有默认值翻转的配置迁移；但有一处可能让 a2a 插件起不来，升级前先看：

- **升级后核对**：
  - a2a 插件正常加载、节点卡已签（启动日志无有效期报错）。
  - 健康提示与团队横幅显示成员名而不只是短 id。
  - 总工与组队顾问会话的工具里有 `lesson_write` 等七个（同时要装好提供它们的 dsh-prompt-templates）。

## preview.27 补充

本版有默认值变化和新的持久化字段，不能像 preview.26 那样「只需重启」就算核完。下面分升级前、配置、持久化与回退、升级后四部分。

### 升级前

- 先备份完整的 a2a home 和当前安装包。重点是 `tasks.json`、`cli-deposits.json`、`idempotency.json`、`superagent/` 目录；回退时这几样会丢掉新字段（见下文），所以要能还原到升级前的状态。
- 在 preview.26 上读 `/__dsh_a2a/state` 的 `legacyInbound`，以及 `a2a-net status` 的 `claims` 行。`legacyInbound` 大于 0，说明还有发送方在发不带 OriginClaim 信封的请求，升级后这些请求会以 `untrusted-origin` 被拒。先升级那些发送方，或者在本机配置里显式写 `originClaimWindow: true`。这个计数在每次重启后从 0 开始，只代表本次进程运行以来的情况。
- 查 home 层 `cordis.patch.yml` 里有没有 `teamScopeInfo` / `teamScopeRouting`，确认它们的值是不是有意设的（见「配置」）。
- 查自动化脚本和团队流程里有没有用到下列已删除或改名的入口，有就先改掉：
  - 工具 `a2a_team_join`、`a2a_team_leave`；名册的 `create` / `add-member`；
  - `/__dsh_a2a/groups`；
  - superagent 控制动作 `add-remote-member`、`remove-remote-member`、`serve-team`；
  - 成员调用的 `a2a_tool_request`（现在只给总工）；
  - CLI `a2a-net report`（本版仍可用，有弃用提示，改用 `tell-host`）。
- 还有发送方用 `[JPFILE-PART` 分件传文件的，升级后一律以 `-32008` / `file-channel-required` 被拒，先改用文件通道。
- 开着 superagent 并用 ygl-trees 的宿主，确认宿主上 `ygl-trees --version`：低于 0.123.0 时派单卡与 preview.26 逐字相同；低于 0.126.0 时启动记一条警告，团队 kb scope 只在 0.126.0 及以上生效。

### 配置

- **`originClaimWindow`**：默认值从 `true` 改为 `false`，没写这个键也按关闭处理（`src/config.ts`、`src/faces/wire.ts`）。只有在确实需要放行不带信封的请求时才写 `originClaimWindow: true`。`originClaimUnboundWindow` 不变。
- **`teamScope`**：新键，同时管路由和信息面两半的团队范围。没写时退回读已弃用的 `teamScopeRouting`、`teamScopeInfo`（默认都是 `true`），各管各的一半；其中任一个是 `false` 且没写 `teamScope` 时，启动日志记一条弃用警告。
  - 属主面板现在写 `teamScope` 一行，面板上关掉就是**两半同时放开**，包括路由。原有的 `teamScopeInfo` 行留在文件里，但写了 `teamScope` 后不再读它。
  - 原来特意把两半设成不同值的宿主，本版仍按旧键分别生效；一旦在面板上改动，就会合成一个值。
- **团队预设**：随包的 `cordis.patch.yml`（bundles 层）改了总工、成员、观察者的人设和挂载的插件：总工去掉 bash、pwsh、jobs，加 `dsh-tool-fs-search`；成员、观察者加 `dsh-command-goal`、`dsh-tool-goal`、`dsh-tool-present`。已经在跑的团队会话要不要重建才拿到新预设，未核实。
- 除上面两个键外，没有必须改的配置。

### 持久化与回退到 preview.26

本版不做迁移步骤，新字段和新文件在启动时或第一次用到时写入。回退到 preview.26 时，按 preview.26（`a680279c`）的代码：

- **`tasks.json`（账本）**：新增顶层字段 `receiptOutbox`、`receiptOutboxRestoreError`、`dispatchReservations`；提醒状态里新增 `deliveryNoticeAt`。
  - preview.26 读取时不认识这些字段也不报错，但它的 `snapshot()` 只写自己认识的字段，所以第一次写账本时这些字段就没了。行上的 `answeredAt`、`receiptDelivery: 'receipt-undelivered'` 在 preview.26 里本来就有，能正常读。
  - 后果：保存着的回执原文在 preview.26 下不再自动补送。重新升到 preview.27 后，这些行显示 `receiptRecovery.state: legacy-unknown`（`RECEIPT_PAYLOAD_MISSING`），不会自动重造回执，只能按原 task 人工核账。
  - `deliveryNoticeAt` 被 preview.26 丢掉后，重新升级时「回执未交付」提示可能对同一行再发一次。这是读代码得出的推断，没有实测。
- **`cli-deposits.json`（CLI 信箱）**：新增 `receiptCommits`、`receiptCommitsCorrupt`。preview.26 不读也不写这两个字段，回退后第一次写信箱就丢掉；信箱回执的预写记录随之丢失，待处理的结算不会被补完。信箱行上的 `admission: 'request-recovery'` 在 preview.26 读取时被丢弃（它只认自己列表里的准入名）。
- **`idempotency.json`**：结果上新增 `delivery: 'not-sent'` 和 `receiptDelivery`。preview.26 恢复时只保留 `status`、`reply`、`error`、`truncated`，这两个字段会被丢掉。重新升级后，这些记录不再有「未发出」的证据，外发恢复会拒绝再发（按失败处理，不会误发）。
- **`request-recovery.json`（及短时的 `.lock`）、`origin-claim-window.json`**：preview.26 不读，留在磁盘上不受影响。重新升级后，关窗度量会把中间这段时间记为无效日，连续天数从头算。
- **`superagent/outbound.json`**：记录新增原批准信息、发送尝试和单次恢复状态。preview.26 读这个文件时不校验字段，但它之后写回时会不会保留这些新字段，未核实。
- **配置**：preview.26 不读 `teamScope`，实际团队范围退回由 `teamScopeRouting`、`teamScopeInfo` 决定（没写时都是 `true`）。所以在 preview.27 面板上关掉过团队范围的宿主，回退后范围会重新打开（`teamScopeInfo` 行里留着的旧值仍按旧规则生效）。在仓库已装的 schemastery 上实测，未知键会原样保留、不报错；宿主自己的配置加载器怎么处理未核实。`originClaimWindow` 没写时，preview.26 的默认值是 `true`，窗口会重新打开。
- **其他**：preview.27 不删除 `groups.json` 和名册数据（`teams.json`），回退后 preview.26 照旧读取；分件过渡规则（16 件以内放行）也随之恢复。
- **回退后失去的不只是数据，还有两道防重保护**（preview.26 的代码不执行它们）：
  - **结果未知的原派发预留**（`dispatchReservations`）：preview.27 对结果不明的原派发保留预留，同一 task / 指纹再来时拒收（「对账原 task，不要重发」）。preview.26 只读不报错，但它下一次写账本就把这块丢了；之后重新升级，同一预留会被重新接受。
  - **单次恢复的围栏**（发送方 `outbound.json` 的 `narrowRecovery`、接收方 `request-recovery.json`）：preview.27 对已接受的单次恢复拒绝同一工单／地址／原文再走一次。preview.26 不认这道围栏，同样的新卡检查直接放行；文件和字段留在磁盘上，并不等于保护还在。
  - 所以「升级 → 回退 → 再升级」这一轮，不能当成某个原请求没发出过、或可以安全再发一次的证据。
- **回退照 [0.7.0 升级检查 §2](0.7.0-upgrade-check.md#2-回退兼容真实-0642-包不是新代码模拟旧读法) 的规则做，不要在活跃 home 上直接降级覆写**：先停掉候选的全部写者，由授权运维把升级前在停写窗口备份的整套 home（账本、会话队列、幂等、CLI 信箱、`superagent/` 等）一起恢复，再用旧版启动；不能只恢复 `tasks.json`。备份之后产生的真实新任务、回执、结果未知的派发和已接受的单次恢复，会回到备份时点：先保留升级后的故障现场，按原 task 人工对账；旧版表达不了的围栏，用请求级的外部暂停或同等的人工控制守住。不要靠删真实状态、自动重试或按摘要重造回执来「修」。
- 升级和回退本身都不需要迁移命令；需要的是上面的停写、成套恢复和人工对账。

### 升级后核对

- `a2a_status` 出现 `Delivery correspondence: retained=N/512 … earliest possible expiry=…` 一行；显示 `unavailable (<原因>)` 时，账本或对应记录有损坏或写失败，先查日志，不要当成空窗口。`/__dsh_a2a/state` 有 `deliveryCapacity`，只有计数。
- `/__dsh_a2a/state` 有 `originClaimWindow`；`a2a-net status` 的 `claims` 下有 `window zero-days=N  measuring since <day>`。升级当天不计入；之后只要不重启，每过完一个完整的 UTC 日加 1。每次重启都会让它重新计数。
- 日志里如有 `untrusted-origin` 拒收，找出对应的发送方，不要靠打开窗口了事。
- `whoami` 报告 `teamScope`。启动日志里有 `teamScopeInfo / teamScopeRouting are deprecated` 时，按「配置」一节决定是否改成 `teamScope`。
- `a2a_probe` 的结果行带 `verdict`；慢节点的行以 `~` 标记，汇总行写 `(N slow)`。
- `a2a_tasks` 里在 preview.26 时期已答复、但回执没送达的行，会显示 `receiptRecovery: legacy-unknown`，接收会话空闲时收到一次 `[A2A receipt delivery blocked]` 提示，每条只发一次。这是预期行为：不要重做业务、换 ID 重发或改投。
- 日志里不应出现 `receipt outbox is corrupt`、`receipt mailbox journal is corrupt`、`request recovery journal corrupt`。出现时自动重放会被拒绝，要按原 task 核账。
- 开着 superagent 的宿主：团队状态里有 `ygl`（读到的 ygl-trees 版本）和 `executor.queued`（每张排队工单的原因）；团队页对排队过久的工单显示原因。成员会话的工具列表里是否真的出现 goal / present，本版没有在真实会话里确认过，请顺手看一眼。

## preview.25 远程测试补充

- 本次属主已明确授权合并发布预览版，节点安装和激活由属主另行安排；未获授权不要在本机或远程生产 profile 自动安装/重启。新头独立复核仍在队列，不把该授权记录写成非作者 PASS。
- owner-proof 改为宿主验证原请求：缺少 Host Connection `admit` / `browserPeer` 能力时返回 `503 owner-auth-unavailable`，无无登录兜底。
- 先备份完整运行 home 和当前安装包，安排可恢复激活；已知生产团队热重载异常未由本次修复，不能假定热重载安全。
- 用新的自有浏览器 context 登录原域名/转发端口；先用原生会话 API 的成功响应确认登录，再只读查卡片、生成并确认不存在的 `diagnostic-nonexistent-<uuid>` ID，以同域请求提交该诊断 ID。HTTP 200 / `code: stale` 仅证明通过鉴权且在不存在卡片处停止，不是实际确认决策成功。不要向诊断工具传真实卡片 ID，不外传 Cookie/token。
- 同一可信 authority 下，无 Cookie、无效/过期 Cookie 应拒绝；外来 Host/Origin、API 身份应拒绝。不要修改反代 Host、trustedHosts 或关闭 owner-proof 来制造通过。
- `a2a_teams` 升级后还应覆盖「有已验缓存、再令对端不可达」场景；仅对端在线时全量列出成功不够。
- 指纹核对如有 Source 状态变化须单列，不假定整个 superagent 目录零写入。
