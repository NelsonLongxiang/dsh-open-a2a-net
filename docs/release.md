### 新功能

#### 已准入任务的回执免发送方 team-scope（#853，上限 #859）

- CLI 身份的 home 宿主转发回执时，若同时满足：消息解析为回执；本宿主台账有这张任务的入账行且仍欠着；欠它的正是发送方；发往入账行记录的回执目标（含 `@<fp8>` 精确比对）；消息只含回执本身（至多两行、无附件）；传输编号与回执相符——就不再由发送方的 team-scope 重判。其余一切照旧由 team-scope 判（默认拒）。
- 上限：确认一次；每个欠单的不同 attention 问题至多 `receiptBypassAttentionMax` 个（默认 20，#859）；进度至多 `receiptBypassProgressMax` 条（默认 20），两条间隔不短于 `receiptBypassProgressIntervalMs`（默认 60000）。已放行的同一条回执重发是同一条回执。超出的按 team-scope 判并记告警。三个键各自独立：`receiptBypassProgressMax` 为 `0` 时进度回执一条都不免检，`receiptBypassAttentionMax` 为 `0` 时 attention 回执一条都不免检；`receiptBypassProgressIntervalMs` 为 `0` 时取消间隔限制（条数仍限），取极大值则首条之后的进度都不再免检。只有非有限或负值回落默认；两个上限取极大的有限值等于不限。把两个上限设为 `0` 只收回进度与 attention 的免检，确认与结果回执仍按上述条件放行，不是关闭整个放行。

#### 总工与组队顾问可以闭合自己的体会与自查轮次（#864）

- `lesson_write`、`lesson_none`、`lesson_keep`、`lesson_timeline`、`lesson_type_propose`、`selfcheck_write`、`selfcheck_conclude` 进入总工与组队顾问的工具名单。七个工具都只作用于调用会话本身（会话号取自调用方，不接受会话号、路径或命令），新体会类型只到待批。不算团队专属工具，非团队会话与成员、观察者照旧。工具本身由 dsh-prompt-templates 提供，没有它就没有这些工具。

### 修复

- **转发的回执只在确实发出后才结清（#853）**：此前转发失败也可能提前结清欠单。没发出去时会释放这条回执的传输编号，重试不再被当成已失败的重放丢掉；发送回执失败时立即报健康错误并保留重试，重试成功后告警清除，24 小时规则不变。
- **结清证明跨归档轮转保留（#806，修 #805）**：已结清的任务被挤出 64 条归档后，不再被当成未跟踪的新投递；此前 64 次归档轮转后，新出站活会在发出前被拒。重放与重新跟踪被拒（`terminal; no replay`）。
- **恢复许可的到期取同一次时钟（#815，修 #782 的一个确定成因）**：许可的签发与到期各取一次时钟时，差 1 ms 就签出 3600001 ms 的许可，被读取侧判为损坏，`/a2a/query` 答 unknown-task。
- **节点卡有效期无效值拒绝启动（#839）与上限（#850）**：见下「行为变化」。
- **成员名显示（#846、#851、#861）**：健康提示与团队横幅写成员的席位名或会话标题，不只是短 id；所有显示成员名的地方统一清洗（换行、制表符变空格，去掉控制符、双向控制符与零宽字符，至多 120 字符），清洗后为空就显示 id；去重键仍是 session id。
- 文档：发布闸门写明直接发布钉定 tgz、不在本地重打包（#840）。
- **发布包里的示例地址（发版评审 R4，属主决定）**：`nexus-stage/scripts/mockhost.py` 的演示数据与两处注释（`nexus-stage/src/planning-card-text.ts`、`src/config.ts` 进入 `lib/types/config.d.ts`）原用私网地址形式的字符串，本版改为 RFC 5737 文档保留地址（192.0.2.x、198.51.100.x）；这是发版分支上的改动，同样的改动另行回灌 next/0.8。
- 测试：#831、#834、#835、#836、#841、#842、#845、#848、#858、#860、#862（补评审留下的测试缺口；#835 去掉全量 verify 里的 TimeoutNaNWarning）。

### 行为变化与升级注意

- **节点卡有效期 `cardTtlMs` 越界时 a2a 插件拒绝启动（#839、#850）**：只接受 100 至 8_589_934_591 ms（约 99.4 天）之间的整数毫秒。缺失、非数字、小数、0、负数、小于 100，或大于 8_589_934_591（此时每 TTL/4 一次的重签定时器会溢出成每毫秒一次）时，启动报错并点名该键，不截短、不回落 48 小时。走配置 schema 取默认 172800000 的宿主不受影响；手写了这个值的部署升级前先核对。
- **CLI 身份发来的、属于已准入任务的回执更多直接放行（#853、#859）**：上限与开关见上；要让进度与 attention 回执都交回 team-scope，把 `receiptBypassProgressMax` 与 `receiptBypassAttentionMax` 设为 `0`（确认仍放行一次）。超出上限时日志多一条告警。
- **总工与组队顾问多出七个工具（#864）**：要配合含这些工具的 dsh-prompt-templates 才实际可用。
- **按名字指名成员（#861）**：路由与派单也接受清洗后的显示名；两个成员清洗后同名时按名字指名返回「无匹配」，须改用 id，成员列表里会在重名者名字后附 id。
- **持久化（#806）**：台账的投递记录新增可选的终态证明。回退到 preview.29 时旧代码不保留它，已挤出归档的已结清任务可能重新被算进回执保护名额（#806 写明的兼容说明）。升级只防止新的误计数，不会补造升级前没有留下的终态证明：已经卡在回执保护名额里的旧记录不保证随升级或重启自动清掉。

### 本版已披露限制

- **凭据访问审计卡「停掉这个会话的工单」的缺陷在本版仍在**：属主对同一会话第二次选这一项时，可能按指名记录停掉已交给别的成员的工单。修复（#865）在截点之后，留 preview.31。
- 回执放行在 `src/index.ts` 里的审计、告警与配置接线没有行为测试钉住（去掉接线的变异存活，#859 已披露）；补测试的 #866 在截点之后。
- 回执放行的计数在内存里，重启清零；每个欠单各自计数，一个身份欠着 N 个任务时最多放行 20×N 个 attention 问题（#859 评审记下）。
- README 中节点卡有效期的配置行尚未写上下限（已另提）。
- 真实宿主验收未跑（NOT_RUN）：两台宿主间的回执放行与告警、#806 在 13080 上的效果、总工与组队顾问升级后实际调用七个工具。

### 修复与改进

#### A2A 投递与回执

- **已写好的回执不会因投递失败而丢失（#708）**：
  - 会话写出的终态回执连同原投递 ID，先存进本机账本，再去投递。
  - 投递结果不明时，只按原传输查询对账；不新发一次 POST，不换 ID 重发，不重做原业务。
  - 投进 CLI 信箱的回执先写一条预写记录；写失败或重启后，只补完那一次结算，不再插入第二份。
  - 已经答复、但回执还没确认交付的任务，与「还没做完」的催办分开处理。接收会话空闲时收到一次 `[A2A receipt delivery blocked]` 提示，每条只发一次，不需要回执。
  - `a2a_tasks` 的行多出 `receiptRecovery`，取值为 `retained`、`blocked`、`legacy-unknown`、`corrupt`。旧版本留下的、没有保存回执原文的行显示 `legacy-unknown`，不会按摘要重造回执。
- **投递对应窗口满了能看到（#746、#747，#713 阶段 A）**：
  - 每台宿主保留的任务投递对应记录上限是 512 条、保留 24 小时。窗口满时的拒收文案不变，另带 `code: 'correspondence-capacity'`，拒收发生在任何入队之前。
  - `a2a_status` 新增一行 `Delivery correspondence`：已占用数与上限、任务占用数、已过期未清数、最早可能到期时间，窗口满时标 `FULL`。宿主状态面新增 `deliveryCapacity`。两处都只有计数，不含任务、会话或消息 ID。
  - 这个拒收从本机同步/异步投递、线上同步/异步响应、客户端解码，一直到多宿主汇总，全程以 `refusal` 字段带着（`notSent: true`）。提示写明这次什么都没发出、最早可能到期时间不保证有空位，也不要靠取消任务、换 ID 或改投别的席位腾位置。
  - 汇总多个候选宿主时，只有这是唯一一个失败才带 `refusal`；否则只给 `capacityRefusals` 计数。
- **`a2a_probe` 给出四值判定（#729）**：
  - 每个实际探测过的行新增 `verdict`，取值为 `reachable`、`slow`、`rejected`、`unreachable`。
  - 新增可选参数 `maxLatencyMs`，默认 2000，上限 60000。`slow` 表示对方应答了但超时，这种行仍是 `reachable: true`。
  - 被团队范围拒绝、没有实际探测的地址不给 `verdict`。
  - 同时关闭 #61、#63，各项最终结论写进协议文档。
- **同机画布队友可以按句柄互发（#741）**：出站范围检查以前只把远端画布成员映射成句柄，本机成员仍按会话 id 比对，所以同机两个画布队友按句柄互发会被拒，以前要靠共享名册才能通过。现在与入站准入一致，两种写法都认。
- **OriginClaim 关窗度量，重启后也不清零（#727，#64 第二步）**：
  - 三个计数 `legacy`、`unbound`、`boundMiss` 按 UTC 日写进 `<a2a home>/origin-claim-window.json`，保留 30 天。
  - 宿主状态面新增 `originClaimWindow { since, zeroStreakDays, days }`；`a2a-net status` 在 `claims` 下新增 `window` 行。
  - 宿主没运行的日子会中断连续天数，每次重启也都会中断。

#### superagent 团队

- **已批准、但没发出去的外发请求可以找回（#705）**：
  - 团队页把「核对原外发」「恢复原批准外发」与工单重派分开。两个操作只有浏览器属主能做，只接受原卡片和原 task，不能换目标、原文或发送身份。
  - 新提出的外发请求会保存原批准信息（批准时间、团队、原文）和每次发送尝试。恢复前重新核对：原批准、提议人、原目标与原文、工单仍开着、A2A 来源开着且没暂停。
  - 只有在任何转发之前就失败、能证明「没发出」的尝试，才允许再发。结果未知、记录缺失或已过期，都不算可以再发；账本里还有这条请求的行时也不再发。
  - 没有原批准信息的旧失败记录不能自动恢复。这类记录另有一条单次恢复通路：发送方属主先核账，接收方属主再确认，许可最长 1 小时、只能用一次，不建立长期链接或成员关系。
  - A2A 来源关着或暂停时，批准会在保存决定之前就被拒，原卡片保留，重新打开来源后可以再批。
- **排队的工单说明在等什么（#744）**：
  - 状态的 `executor.queued`、`superagent_read` 和 `a2a_ticket_read` 给出每张排队工单的原因：`member-busy`、`member-absent`、`no-repo-member`、`repo-busy`、`all-busy`、`at-cap`、`delivery-refused`、`launch-stalled`、`paused`。
  - 排队超过安静时限的工单进入健康检查，按成员或仓库合并成一条 `tickets-queued`，附数量和最早一张；团队页和右栏横幅同步显示。
  - `superagent_assign` 的说明改为：还没开工的工单随时可以改派给任何成员。行为本身没变。
- **投递途中结束的安静回合不再丢（#745，#742）**：成员的输入还在投递时结束回合，这个回合结束以前会被丢掉，`maxConcurrent=1` 时成员闲着却一直占着团队唯一的执行槽。现在投递完成后，若投递没失败、绑定没变、没有未送达的输入，并且那个回合确实已读到这次输入，就补结算这个回合；否则由输入唤醒的新回合自己结算。
- **普通成员可以提议新需求（#718，#717）**：`a2a_ticket_request` 加入成员工具，提议只进总工候选，接不接、派给谁仍由总工决定。提议不会结束、停止或改派提议人手上的工单；每个提议人最多 5 条未结。远端成员经已有的签名转发通道提议；Pi 席位不能提议。
- **总工能读文件，成员预设补上 goal 与 present（#736）**：
  - 总工的工具白名单加入 `read`、`glob`、`grep`、`skill`。预设补挂 `dsh-tool-fs-search`，去掉原来挂着却从来调不了的 bash、pwsh、jobs；写文件、编辑和执行命令仍然全部拒绝。
  - 成员和观察者预设补挂 `dsh-command-goal`、`dsh-tool-goal`、`dsh-tool-present`。
- **总工人设写进沟通渠道规则（#707）**：总工预设人设里直接写明普通 A2A 请求、同队远端成员、经批准的外发求助、已登记的子团队各走哪条路，不再依赖总工默认读不到的技能参考。三个角色的人设都追加了同一段说明：团队的 CLI 信箱只是已批准团队传输的实现，不能拿来绕开角色、批准或接收方准入。新增技能参考 `superagent-communication.md`。
- **ygl-trees 按已装版本出卡，各团队有自己的 kb scope（#739）**：
  - 宿主启动时读取 `ygl-trees --version`，结果放进团队状态的 `ygl`。0.123.0 起派单卡去掉 `project use` 一步；低于 0.123.0 或读不到版本时，卡片和以前逐字相同；低于 0.126.0 时记一条警告。

- **两处启动和调度故障（#740）**：成员结束回合时，读作业列表不再因丢失接收对象而抛错，持有的等待中工单能正常挂起，下一张工单可以拿到执行槽。卡片缓存提前到恢复已加载会话的角色之前初始化，堵住 #617/#628 同类启动故障的另一个入口。

  - 转发闸的两种拒绝分开说明：「no bound CLI signature」（改拨号地址或 `originClaimAudiences`）和「not an online local CLI deposit」（执行 `a2a-net publish`）；#635 的续期重试只在后一种时触发。线上错误码不变。

### 工单跟随 PR，并可送审（#516、#517、#519，设计 [superagent-pr-follow](design/superagent-pr-follow.md)）

- 成员用 `a2a_ticket_report` 的 `pull_request` 报告它开的 PR 后，工单等到这个 PR 合并或关闭才结束，等待期间不占成员。请求方在此期间收到的是确认（acknowledged），PR 结束后才收到正式结果。
- 团队宿主用运维者登录好的 `gh` 读这些 PR（60 秒一轮，读失败退避到 15 分钟，并显示在「团队」页；读失败不会结束工单）。插件不存令牌。
- PR 上的新评论和评审会送回工单的成员。只有 `allowed.github` 里的登录名算人，默认为空。
- 成员用 `a2a_ticket_ack` 接手 PR 上人写的评论时只做记录，不往 PR 上发内容；接手后工单等成员报告完才结束，没接手的评论在工单结束时交给总工（#519）。
- 设置 `reviewer`（一个 A2A 地址，须在属主的链接集内）后，每个工单的 PR 在每个新 head 上都发一次送审请求，只带 PR 引用。评审结果显示在「团队」页和工单上，只供合并的人参考：成员和宿主都不会合并。

### superagent 总工看得见自己读到的东西（总工判断力验收）
- 修正：superagent 各工具此前只把「ok」交给模型，总工用 `superagent_read` 读到的工单与候选、`superagent_route` 的工单号和被拒项都看不见。现在模型看到调用返回的内容（JSON，超过 12,000 字符截断并注明）。
- 候选卡片列出团队在其他会话线上的在办工单（最多 20 张，新的在前）；与在办工单重复的请求要并入（`attach`），不再接成第二张。
- 候选卡片写明：人只提问、不要求干活时，用 `superagent_reply`（`answer`）回答后仍要用 `superagent_route` 判为 `ignore`；每个候选都以一条 route 结束，否则到期后回来重判。
- 总工转问（`superagent_reply` 的 `attention`）：发给人的只有正文；正文里没有成员问题原文时，宿主把原题放在正文前面，人在自己的会话线上就能看到要回答什么（验收 RJ8）。
- 团队设置改动会告诉受影响的在办工单（上游 PolicyEffect）：工单所依据的规则改了或关了、团队不再接 agent 发起的工作（接收模式不是 auto）、请求方不再被允许发起工作——成员收到一条用文字写明的 `[superagent input]`；只告知，不停止也不扩大工单。此前宿主改设置时不告诉在办工单。

### superagent 团队：智能体预设（#432、#437、#438）

- 插件在 bundle 层随附两个智能体预设：`superagent-router`（总工：文件只读，前台命令与等待最多 5 秒，不开子代理）和 `superagent-member`（成员：工作工具，前台命令 5 秒后转后台，不开子代理），改编自上游 dsh-superagent 的主会话与执行器预设。角色边界由预设本身决定，不靠卡片里的提示词。
- 宿主在保存设置、画布加成员、`serve` 时核对：总工或成员的会话跑在别的预设上就拒绝；为别的团队服务的会话不是成员预设时不接新活（停止仍可达），状态报 `servesProblem`。未加载的会话、或宿主没有预设注册表时不检查。

### superagent 团队：团队就是一支画布团队（v5，#441–#447）

- 属主在画布上组队（总工与成员，本机或其他主机），在「团队」页绑定画布并从中指定总工；成员从画布读出、不再在设置里点名，`add-remote-member` 取消（远端成员就是画布远端槽，公钥由画布钉住）。画布增删成员即成员池增删；工单进行中被移出的成员收到停止通知，工单在另一成员上重派。一个会话只担一个团队角色。
- 团队的 A2A 地址就是画布地址 `<zone>/canvas/<名字>`（其他主机写 `@<fp8>`）。发到这里的请求进团队信箱、不落成员会话；团队的回执和后续由宿主进程面代团队发出（`onBehalfOf` 按请求方原样拼写），请求方账本按 host-face 结清。直接发给团队内部句柄被拒（`[superagent-team-address]`）；同步路由立即答复已送达。
- 其他主机上声明了团队的会话可向团队画布提需求（需要团队宿主属主以画布远端引用建立链接）；请求方主机只把团队的代发回执当作那一条请求的答复接收。
- 成员主机按画布 id 为团队服务：`serve { team: '<zone>/canvas/<名字>@<fp8>' }` 取代 `serve-team`。
- 规划视图标出团队画布（「superagent 团队」）和总工、成员的角色与仓库。
- 设计记录见 [superagent-v5-canvas-team](design/superagent-v5-canvas-team.md)。

### 0.8.1 已披露限制

- 0.8.0 一节列出的限制全部仍然适用。
- 预览版尚未在两台真实机器之间验收：跨主机成员的现场验收是同一台机器上的两个宿主进程。
- 工单跟随 PR 依赖团队宿主上已登录、能读到目标仓库的 `gh`；读不到时工单保持打开，「团队」页显示原因。
- 总工和成员都是长期会话，上下文会一直增长，插件不主动压缩或换会话，靠宿主自身的压缩。验收环境里总工跑到约 53 万 token（配置的上下文窗口为 100 万）时还没有压缩，单步耗时没有因此明显变长；几个大上下文会话同时用一个模型服务时，单步会到几分钟。
- 一次批量并入工单的多条消息，成员只看到第一条的正文。
- 成员报告转给总工的那一步不持久，团队宿主此时重启会丢这一次转告（工单和报告本身还在）。

### 路由（#372、#375、#405）

- 进程内投给普通 CLI 信箱的消息不再记欠账（#405）。
- followup 抛异常后的宿主接纳观察：只有本次预留的精确会话/MessageId 出现在该会话 inbox 或事件流，才返回 DELIVERED 与 `acceptance:inserted`，提示后续未确认、原 task 对账；不代表消费或完成。证明不了仍失败并带 `acceptance:unknown`，提示“接纳状态未知，请用原 task id 对账，不要换 id 重派”，新调用方停止候选 failover；已知插入前拒绝不改。契约与旧客户端限制见[接纳观察](protocol/followup-admission.md)。不新增状态，0.2.2-rc.1 仅源码判断、未运行验证，不进入0.7.0。
- 已披露限制（#375，全局 2026-11-06）：返回 `acceptance:"inserted"` 时，主机已接纳输入；但如果接收方没有出生行（例如出生提交失败），这一笔不会触发 nudge，也不会挂自动回执，只能由人按原 task id 人工对账。
- 节点升级说明（#375）：旧主机（0.7.0 及更早）不认识 `acceptance:"unknown"`，收到后仍可能 failover 到其他候选目标。新主机才会停止 failover，并提示“接纳状态未知，请用原 task id 对账，不要换 id 重派”。建议调用方和接收方两端都升级。

- 普通 Agent 同步等待的主机占位输出（flush 超时、会话 dead、aborted / failed 读取轮、textless）返回已有 `TASK_STATE_DELIVERED` 且不带 `reply_final`。CLI 与 `a2a_route` 同步路径提示“已送达、未得到最终答复，请按 task id 对账”，不是失败重投或完成。已有出生/自动回执的 forwarded sync 带 `receipt:routed` 并保欠账；plain sync 不新建出生/自动回执，带 `receipt:none`，调用方记可见 receiptless 行而不计欠债。除明确 `receipt:none` 的非债兼容路径外，只有复用现有阅读轮归属得到的真实 own-turn final 才允许把普通同步答复当已付。native-teams 权威 round 与 CLI mailbox 接纳语义不扩大变更。
- 新版 CLI 的 sync 转发等待超时由原来的非 0 退出码改为退出码 0，并提示“已送达、未得到最终答复，请按 task id 对账”，依赖退出码判断成败的脚本需要据此调整。
- HTTP 等待和自动回执用途分离：等待到期不删除后续 receipt 归属跟踪；后者按原任务终态、取消、TTL 或卸载清理。晚到真实读取轮 final 仍走同一固定身份回执和原有有限退避；占位、未消费、已关闭的空/失败读取轮不生成正式回执，不采用其他任务/后续轮输出。#351 提醒只提示本人对账，不新造正式回执。
- 旧客户端兼容：0.7.0 及更早 CLI 收到这种含 `result.text` 的 DELIVERED 同步响应时会打印回复并在 stderr 提示未 settled，通常退出0，不自动重投；旧 `a2a_route` 返回 `ok:true` 和 DELIVERED，保留可路由回调的欠账，但旧 `trackOwedTask` 不识别 plain sync 新的 `receipt:none`，仍可能挂幽灵债；因此普通同步两端也应同步升级，不能仅凭旧文案当完成。旧版没有新的明确中文同步对账提示。如果走旧客户端的 `delivered:true` 分支，其文案可能仍称 async；以状态/task id 对账，不能把主机文字当业务完成。旧转发 home 若误收到旧对端的无 `reply_final` COMPLETED 仍可能按旧规则 receiptless，因此建议两端同步升级；本候选不改0.7.0已构建字节或代替后续发版授权。
- 边界见[同步回复契约](protocol/synchronous-reply-contract.md)。同步回复片段不涉及 followup 泛化 throw 的接纳未知（本节另列接纳观察候选）；#369已覆盖窗口、不自动补出生及重启不恢复补发定时器等边界不变。不新增任务状态，不 tag / publish / 部署。

## 0. 0.6.41 升级提示

- **安全（尽快升级）：对端请求不再跟随重定向**（#318 评审 R4）。以前所有对端请求都会跟随 3xx，`X-API-Key`（舰队 key 或链路 key）和签名头会被带到 `Location` 指向的主机；任何一个对端回一个跨源 302，就能把 key 引到第三方。0.6.40 及更早版本都有这个问题。现在所有对端请求都在 `peerFetch` 统一设置 `redirect: 'manual'`，3xx 一律按 HTTP 失败处理。**升级须知**：`peers` 里写的地址必须是对端的最终地址。例如走 Caddy 的节点要写 `https://域名`；写 `http://域名` 会因为被 301 到 https 而连不上。
- **#306 同步答复绑定消费任务的轮次**：带 task id 的同步请求只取真正读到该任务的轮次的答复，不再把目标正在处理的其他工作或下一轮的文字当成答案。同步等待与自动回执采用相同归属窗口；没有 task id 的旧调用仍使用原回落行为。
- **忙碌目标会有更多诚实的超时**：若真实答复超过既有 15 秒传输窗口，调用方可能收到 `-32005` / DELIVERED-UNSETTLED，而不是一段无关文字。投递不因此撤销；沿原 task id 对账，使用 async + inbox 等真实回执，切勿因超时新发任务。窗口和准入默认值不变。
- 回执仍完整保存；同步确实取得本任务的完成答复后，后续同任务回执继续按 #305 标记 `sync-answered`，不丢弃。placeholder、未消费及失败轮次不作为本任务完成证据。
- **链路 key `linkKeys`**（#317）：按对端单独配置 key，公网节点不必持有舰队 apiKey 也能互联。发往 `linkKeys` 里某个 origin 的请求带该链路 key；本机对端接口只在调用方 OriginClaim 验签通过、绑定到本次请求（受众绑定的 v2 信封，不接受只有 v1 的信封或挪用到别的路径的信封）、且签名者正是该 origin 时接受链路 key，POST 还要求 Sig3 绑定请求体；控制路由一律不接受。两端都要升级到 0.6.41，并配置同一把链路 key。不配置 `linkKeys` 的主机行为不变。
- **远端会话日志读取带上 key 和签名**（#318 评审 R2）：工作台读取对端会话日志的代理请求以前既不带 key 也不签名，对开了 key 的对端一直会 401。现在会带 OriginClaim，以及按目标选出的 key。
- 验证器：`scripts/verify-probe.mjs --release-audit` 留存发布物证据（#319），可以在发布后核对候选 SHA、tgz 哈希、文件清单、3081 验收以及两个 registry 回读的字节是否一致。

## 0. 0.6.40 升级提示

- **安全：反代转发的请求不再享受回环信任**（#308）。0.6.39 及更早版本里，同机反向代理（Caddy、nginx、隧道代理）以 `127.0.0.1` 连接节点，所有公网请求都被当成本机：配了 key 的主机会把 apiKey 写进工作台 HTML，没配 key 的主机控制面对公网完全开放。现在请求只要带 `X-Forwarded-For`、`Forwarded` 或 `X-Real-IP`，就不给回环信任；经代理带 key 访问照常可用。**对外开放的节点请尽快升级。** nginx 必须设置 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`，Caddy 默认会带。经 pocket 隧道打开工作台不受影响（pocket 不写转发头）。

## 2. minimumReleaseAge × 锁重生成发布窗口

锁重生成会把「窗口期内的新版包」写进锁（如 fast-uri@3.1.9）；此后**所有**干净检出
`pnpm install --frozen-lockfile` 都被 minimum-release-age 策略拦死——不是缓存问题，
是策略按锁内版本的发布时间判定。

纪律：
- 候选期/发布窗口内做干净检出安装，统一带 `--config.minimum-release-age=0`；
- 无法带 flag 的环境（CI 模板等）：把窗口期新包加进 `pnpm-workspace.yaml`
  的 `minimumReleaseAgeExclude` 列表（现列 dsh-\* 0.1.2-alpha.3 六件）；
- 锁重生成提交前，本机跑一次干净检出 frozen install 复核（gold standard）。
